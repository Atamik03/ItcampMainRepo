# Требования к GitLab Runner'ам

Пайплайн (`.gitlab-ci.yml`) использует **два разных типа раннеров** с
разными тегами — `docker` и `deploy` — намеренно разделённых, а не один
универсальный DinD-раннер на всё. Обоснование ниже.

## Почему два раннера, а не один

Задача явно предупреждает: не считать Docker-in-Docker автоматически
лучшим вариантом для deployment, и что DinD требует privileged mode,
несущего дополнительный риск. Разбор реальной архитектуры репозитория
показал:

- **Build/scan** (`docker build`, `docker run` для Trivy/Hadolint, `docker
  push`) реально нужен полноценный Docker daemon — для этого DinD
  (privileged) действительно нужен, тут без него не обойтись.
- **Deploy** (`docker compose pull && up -d`) не требует DinD вообще —
  ему достаточно **прямого** доступа к Docker Engine, уже установленному
  на хосте. Оборачивать это в ещё один вложенный DinD-контейнер не даёт
  никакой пользы, только добавляет привилегированный слой там, где он не
  нужен.

Поэтому: **build-раннер** — privileged DinD, эфемерный, ничего не хранит
между джобами кроме кеша. **Deploy-раннер** — обычный shell executor,
работает НА ТОЙ ЖЕ машине, что и запущенное приложение (сам раннер —
это и есть deployment-хост), без privileged mode вообще.

## Раннер 1: `docker` (build/scan)

| Параметр | Значение |
|---|---|
| Executor | `docker` |
| Тег | `docker` |
| Docker Engine | требуется на хосте раннера (для DinD-сервиса), версия ≥ 24.x; пайплайн сам пинит `docker:27.3.1`/`docker:27.3.1-dind` как job/service images — версия хост-демона раннера должна быть с ними API-совместима. |
| Docker Compose | требуется только в одной джобе (`yaml-and-compose-validate`) — ставится внутри job'а через `apk add docker-cli-compose`, на хосте раннера ничего не нужно. |
| Privileged mode | **Да, требуется** — только для DinD-сервиса (`docker:27.3.1-dind`). Это единственная привилегия, которую вообще запрашивает этот пайплайн, и она полностью изолирована в build-джобах; deploy-раннер её не использует ни разу. Настраивается в `config.toml` раннера: `[runners.docker] privileged = true`. |
| Registry access | Да — `docker login` к `$CI_REGISTRY` (GitLab Container Registry) для push образов; `docker login` к Docker Hub (`$DOCKERHUB_USER`/`$DOCKERHUB_TOKEN`) для Docker Scout. |
| Volumes | Только job-локальный кеш (`.npm/`, `.pip-cache/`, `.trivy-cache/` — см. `cache:` в `.gitlab-ci.yml`) и Docker socket внутри DinD-сервиса (управляется самим GitLab Runner, не настраивается вручную). |
| Постоянное хранилище | Не нужно — раннер полностью эфемерен между джобами (кроме объявленного `cache:`). |
| Системные зависимости на хосте раннера | Только Docker Engine + GitLab Runner агент. Все остальные инструменты (Trivy, Hadolint, Semgrep, Bandit, Node, Python) приходят как образы контейнеров, ничего не нужно ставить на сам хост раннера. |

### TLS для DinD

`.gitlab-ci.yml` использует переменные `DOCKER_HOST=tcp://docker:2376`,
`DOCKER_TLS_CERTDIR=/certs`, `DOCKER_TLS_VERIFY=1` — это официально
задокументированный GitLab/Docker паттерн «DinD с TLS» (не «insecure» TCP
без TLS, который был бы дополнительным риском поверх уже привилегированного
режима). Раннеру не нужна отдельная настройка для этого — сертификаты
генерируются автоматически GitLab Runner'ом и DinD-сервисом при каждом
job'е; единственное требование — чтобы у executor'а был volume для
`/certs`, что GitLab Runner делает сам при `privileged = true`.

## Раннер 2: `deploy` (deployment target)

| Параметр | Значение |
|---|---|
| Executor | **`shell`** (не `docker`, не Kubernetes) — джобы `deploy`/`verify`/`rollback` выполняются напрямую в shell на хосте раннера. |
| Тег | `deploy` |
| Docker Engine | требуется **напрямую на хосте** (не в контейнере) — версия ≥ 24.x, с уже настроенным Docker Compose v2 (`docker compose version` должен показывать v2 — тот же бинарник, что использует `start.sh`/`start.ps1` для локальной разработки). |
| Docker Compose | v2, установлен на хосте (обычно идёт вместе с Docker Engine как плагин). |
| Privileged mode | **Не требуется** — раннер не оборачивается в контейнер вообще, `docker compose` вызывается как обычная команда хоста. |
| Registry access | Да — `docker login` к `$CI_REGISTRY` для `docker compose pull`. |
| Postgres/Redis доступ | Не нужен отдельно — они сами часть стека, который поднимает `docker compose up -d`. |
| Volumes / постоянное хранилище | **Обязательно постоянное**, не эфемерное — `$DEPLOY_PATH` (например `/srv/elou-avt`) должен переживать между джобами: там хранится `./data/postgres` (bind mount БД, см. `README.md`), `./secrets/*` и файл `.last_healthy_sha`/`.previous_healthy_sha` для rollback. Если раннер эфемерный (например, автоскейлящийся docker-machine executor), эти данные потеряются между деплоями — поэтому этот раннер должен быть **одной конкретной, постоянно существующей машиной**, зарегистрированной один раз, не пересоздаваемой. |
| Deployment directory | `$DEPLOY_PATH` (CI/CD-переменная) — например `/srv/elou-avt`. Владелец — пользователь, от имени которого работает GitLab Runner на этом хосте; этот пользователь должен состоять в группе `docker` (см. ниже про security). |
| Права раннера | Пользователь, под которым работает `gitlab-runner`-процесс, должен быть в группе `docker` хоста — это даёт ему полный доступ к Docker daemon (эквивалент root, см. предупреждение ниже). Кроме этого — обычный пользовательский доступ к `$DEPLOY_PATH`. |
| Порт 8080 | Должен быть свободен на хосте раннера — `docker-compose.ci.yml` публикует `frontend-nginx` на `0.0.0.0:8080` (в отличие от локальной разработки, где `docker-compose.yml` сам по себе биндит только `127.0.0.1:8080` — см. `docker-compose.ci.yml`, зачем нужен этот оверрайд). |

### Почему раннер имеет прямой доступ к Docker Engine — и что это значит для безопасности

Джобы `deploy`/`verify`/`rollback` выполняют `docker compose`, что требует
доступа к Docker socket хоста. Членство в группе `docker` **фактически
равнозначно root-доступу к хосту** (любой процесс с доступом к Docker
socket может смонтировать `/` хоста внутрь контейнера и получить полный
контроль) — это не какая-то экзотическая уязвимость этого конкретного
пайплайна, а общеизвестное свойство Docker, отмеченное в самом ТЗ. Из
этого следует:

1. **Этот раннер должен обслуживать ТОЛЬКО деплой этого приложения**, не
   быть общим shared-раннером для других проектов/задач — иначе любой
   pipeline с доступом к тегу `deploy` в любом другом проекте получает
   фактический root на этой машине.
2. Тег `deploy` должен быть **защищённым** (Protected Runner в настройках
   GitLab) — доступен только защищённым веткам/тегам, чтобы feature-ветка
   от любого контрибьютора не могла случайно (или намеренно) получить
   доступ к джобу с root-эквивалентным доступом к продакшн-хосту.
3. Секреты (`DEPLOY_POSTGRES_PASSWORD` и т.д., см.
   `docs/gitlab-ci-setup.md`) должны быть Protected+Masked переменными —
   это ограничивает их доступность защищёнными ветками/тегами тем же
   механизмом GitLab.
4. Docker socket **не** монтируется ни в один прикладной контейнер стека
   (`docker-compose.yml`/`docker-compose.ci.yml`) — только сам раннер
   вызывает `docker compose` напрямую на хосте. Ни backend, ни frontend,
   ни db, ни redis никогда не получают доступ к сокету.

## Итоговая сводка

```text
Runner "docker"                          Runner "deploy"
────────────────                         ───────────────
executor: docker                         executor: shell
privileged: true (DinD-сервис)           privileged: false
эфемерный между job'ами                  постоянный, один конкретный хост
не хранит данные приложения              хранит $DEPLOY_PATH (данные, секреты, .last_healthy_sha)
доступ: GitLab Registry + Docker Hub     доступ: GitLab Registry + Docker Engine хоста
общий/shared — безопасно                НЕ shared — только для этого деплоя, Protected Runner
```
